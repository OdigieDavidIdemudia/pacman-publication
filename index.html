A safe control plane for the file that routes everything.

PACMAN manages a live proxy.pac without owning it. Rules live inside a marked block; the rest of the file is preserved byte for byte. Every change is previewed, executed against representative hosts in a sandbox, written atomically, verified on disk, and snapshotted. This page documents the model, the safety pipeline, what an analysis of a real production PAC found, and what the tool does not claim.

01

Context

A PAC file is executable policy. Every browser in the estate evaluates FindProxyForURL on every request, so one broken line can send a bank's internal traffic through a proxy that cannot reach it — or quietly bypass the proxy for a domain that should never leave the network.

It is edited by hand

PAC files grow by append. A rule is added for one application, then another, with no owner, no test, and no history beyond a comment with a date.

Failures are silent

A missing return, an unanchored wildcard, or a DNS check in the wrong order does not raise an error. It changes routing and nobody notices until a team cannot log in.

The blast radius is the estate

Unlike an application config, a mistake here is served to every client at once and cached by browsers. Rolling back means finding the old file first.

PACMAN's goal is narrow: keep the file that already works, and make the part being changed small, reviewable, testable, and reversible. It is a control plane for a marked region, not a replacement for the proxy or for network design.

One organisation, one file

PACMAN assumes one team owns the server, the PAC file, and the proxy registry. It is not a multi-tenant service and does not attempt to model several estates in one installation.

03

Architecture

The SPA never writes files. It calls the API; the API is the only component with a write path, and that path runs the full safety pipeline. SQLite is authoritative for rules and history; the PAC file is generated output. Nginx serves the result to clients and never talks to the database.

Why this shape

  • One writer. Only the API writes the file, so every change passes the same guard and produces the same snapshot.
  • The file is not the database. Rules are stored logically; the renderer produces directives, which keeps the output stable and diffable.
  • Serving is boring. Nginx serves a static file. A failed admin UI, database outage, or guard problem cannot change routing by itself.
04

Rule model

A rule is a selector plus an ordered route. The route is a list of tokens rather than an enum, because a failover chain is not a different kind of thing — it is three proxies and a fallback in a specific order.

Route kinds are derived from the token list, not stored as separate types.
Kind Tokens Rendered directive
Direct ["DIRECT"] DIRECT
Via proxy [1] PROXY 192.0.2.10:8080
Failover chain [1, 2, "DIRECT"] PROXY 192.0.2.10:8080; PROXY 192.0.2.11:8080; DIRECT

The DIRECT tail is fixed by the model. A chain that ends in nothing is a chain that can take a host offline when every proxy is unhealthy; the renderer will not produce one. If strict proxying is a policy requirement, that is a deliberate product decision, not a default.

Ordering is part of the contract

Rules are emitted in a stable order by selector type and value, so the same database always produces the same bytes. Before a change is accepted, the service rejects duplicates, same-host conflicts, and rules that would be shadowed by an earlier, broader selector — the exact class of defect that turns a hand-edited PAC into archaeology.

A selector type is not a priority lesson you can skip

An exact IP rule renders as host === "192.0.2.10". It matches a request whose host is that address, not a hostname that resolves to it. A /32 CIDR rule is the one that resolves the host. Publishing that distinction is cheaper than debugging it later.

05

Write path

No control in this product matters more than the order of operations on disk. A change is never applied because the form posted successfully; it is applied because the candidate passed the guard, reached the disk intact, and produced a snapshot.

01 / PREVIEW Show the consequence

Entries are parsed and classified. The diff and per-entry outcome are returned before anything is written.

02 / GUARD Run the file

The candidate is compiled and executed in a sandbox against hosts that must resolve to specific directives.

03 / WRITE Replace atomically

Write to a temporary file and replace under a lock, so a reader never sees a half-written PAC.

04 / VERIFY Read it back

The bytes are re-read and hashed. A mismatch restores the previous file and fails the request.

05 / SNAPSHOT Make it reversible

A full-file version is recorded with the actor, reason, and rule payload, before the operator moves on.

The file is spliced, not regenerated

The base PAC is preserved exactly. The service locates the markers and replaces only the region between them, keeping comments, helper functions, and the fallback return untouched. A file with legacy markers is upgraded in place on its next write; a file with no markers is adopted, not overwritten.

Last-known-good is a fallback, not a promise

Every successful write is a snapshot, and restoring one re-runs the same guard rather than copying blindly. Retention and the reaper are bounded, so this is an operational recovery path, not an archival system.

06

Markers, repair, and legacy files

Markers are the contract that makes byte-preserving edits possible. They also create the first real problem: most production PAC files do not have them.

Where the block goes is a decision

The repair flow offers two policies, and they are not cosmetic:

  • Additive inserts the block immediately before the function's unconditional fallback return. Existing rules keep precedence; managed rules only decide what is left.
  • Authoritative inserts it at the top of FindProxyForURL, so managed rules win over the hand-written ones.

The naive choice — before the closing brace — is wrong for the most common PAC shape. If a file ends with return FPProxy();, a block appended after that return is unreachable code. The planner now detects the terminal statement, inserts before it, and reports the line it chose. If no reachable point exists, it refuses rather than writing a block that can never run.

Reading a legacy file without executing it

The analyzer parses a safe subset of the PAC idioms into rule candidates, resolves helper functions to the literal they return, and lists everything it cannot represent instead of dropping it. On a production file this produced a complete inventory and a defect list before any migration was attempted.

What the analyzer recognises, and what it reports as not representable.
Construct Becomes Result
host === "x" Domain rule ● Convertible
dnsDomainIs(host, "x") Domain rule ● Convertible
shExpMatch(host, "*.x") Wildcard rule ● Convertible
isInNet(ip, net, mask) CIDR rule ● Convertible
myIpAddress() — ◐ Client-aware
shExpMatch(url, …) — ◐ URL condition
isPlainHostName(host) — ◐ No rule type
isInNetEx() / time ranges — ◐ No rule type

The lint pass is where the tool earns its keep. It flags the defects that are invisible in review: 

if (shExpMatch(host, "publishers.example.com"))

if (isPlainHostName(host) || shExpMatch(host, "*.local"))
    return "DIRECT";

The first if has no body, so the entire internal-host block becomes its body and only ever runs for that one hostname. The file parses, serves, and silently proxies every short name and .local host it was meant to keep direct. PACMAN reports it as an error with the line number: “This if has no body, so the entire next block becomes its body.”

07

Proxy health and the balancing boundary

Health data is advisory. A PAC file is static, so nothing in the probe path is consulted while serving. The probes exist to warn before a rule is saved and to make a failover order defensible.

  • One TCP connect, ≤1.5 s, no HTTP round trip. Cheap enough to run on create, on address change, and on a five-minute sweep.
  • Smoothed latency. A new sample moves the average by 30%, so one slow connect does not reorder the registry.
  • Failure history. Consecutive failures and lifetime availability are recorded alongside the last probe.
  • A score, not a verdict. Reachability first, then latency, then stability. The UI shows the number and the evidence side by side.
What PACMAN cannot do: load balance

A PAC file has no runtime load balancing. The browser walks the directive list and stops at the first proxy that answers, so the only lever is order. A file that rotates that order per client is doing PAC-level client spreading, and that logic lives outside the managed block — which is why the analyzer reports myIpAddress() as not representable instead of pretending to convert it.

08

Deployment

One container, one data directory, one published admin port. The PAC file is a bind mount so the web server can serve it without going through the application. 

docker compose -f deploy/docker-compose.yml up -d --build

On boot the application applies numbered SQL migrations, ensures its directories exist, and refuses to start if the validator configuration is unknown. The SPA shell is served no-cache; hashed assets are immutable. That combination is deliberate: a rebuilt UI must never be masked by a cached shell.

Operational surface.
Concern Default Note
Admin port Bound to loopback Publish it deliberately; put TLS in front before exposing it.
PAC delivery Static file via web server Short cache window; clients refetch on their own schedule.
State SQLite + versions directory Back up both; the database alone cannot restore a file.
Validator QuickJS Structural mode exists for development and is reported as degraded.
Migrations Automatic at startup Versioned; a failed migration is retried rather than silently skipped.
09

What the review of a production PAC found

PACMAN was built alongside a review of a real, working, hand-maintained PAC file. The file had been in service for months and passed every visual inspection. Running it found the following. Hostnames are replaced with reserved examples; the defects are unchanged.

PAC-01

One missing return disabled a whole block

An if without a body swallowed the next section — eleven rule groups, including every short hostname and *.local entry — so those hosts were being proxied instead of going direct.

Impact Internal applications routed through a proxy that could not reach them; no error anywhere.

✕ Fail

PAC-02

An unanchored wildcard allowed a look-alike bypass

shExpMatch(url, "https://partner.example*") also matches partner.example.evil.test, sending an unrelated domain DIRECT.

Impact A proxy bypass for any domain that begins with the literal string.

✕ Fail

PAC-03

DNS resolved before hostname decisions

dnsResolve(host) ran at the top of the function, so every request paid for a lookup even when the decision was name-based, and proxied traffic leaked DNS to the client resolver.

Impact Unnecessary latency and a resolver dependency on every request.

◐ Partial

PAC-04

Load spreading relied on the client address

The proxy order was rotated by myIpAddress(). Engines differ in what that returns — commonly 127.0.0.1 in Chromium-based browsers — which collapses every client onto one order and one first proxy.

Impact Uneven load; the rotation can look correct in code and be inactive in the estate.

◐ Partial

The lesson is structural, not personal

Both serious defects are invisible to review and obvious to execution. A tool that can run the file against known hosts, and lint the constructs it understands, catches them before they are served.

10

Scope & limits

The honest boundary matters as much as the feature list. The following are deliberate.

In scope

  • Managing a marked rule block inside an existing PAC file.
  • Validating a candidate against representative hosts.
  • Versioning, restoring, and auditing every write.
  • Reading legacy constructs and reporting what cannot be converted.
  • Advisory proxy health and ordering suggestions.

Not claimed

  • Being the proxy, the DNS resolver, or the network policy engine.
  • Runtime load balancing between proxies.
  • Full PAC language conversion (arbitrary JavaScript, time ranges, URL logic).
  • High availability, clustering, or multi-tenancy.
  • Protecting a PAC file that is edited outside PACMAN after the fact.
  1. The guard proves behaviour, not intent. It executes a candidate and checks the directives it observes; it cannot know that a rule was a bad idea.
  2. Structural mode is degraded by definition. With both validators available, QuickJS is the production path; without it, the result is reported as degraded rather than presented as equivalent.
  3. Markers are the limit of authority. Bytes outside the markers are preserved and unmanaged. A hand edit inside the block is detected as drift, not repaired silently.
  4. Browser caching is outside our control. A correct file can still be served from a client cache; the PAC cache window is a deployment parameter, not a guarantee.
  5. The analyzer is a subset. It recognises the idioms that appear in operational PAC files and reports everything else. It never executes the script to analyse it.
  6. An exact IP rule is exact. It matches a literal host, not a name that resolves there. A /32 CIDR rule is how you express “any host that resolves to this address”.

12

Summary

PACMAN treats a PAC file as production code: a small managed surface, a guard that runs the candidate before it is served, an atomic write that is verified on disk, and a snapshot that makes the change reversible. The part it deliberately does not do — load balancing, DNS, proxy health enforcement — is stated rather than implied. On a real file, the same machinery found two defects that had survived months of review, which is the argument for the design.
